## Credential and ownership contract

`/api/providers` requires a current invited Better Auth session for every method. GET returns only server-derived resource availability, reviewed model catalog and that owner's safe key metadata: provider, masked final four characters, revision, test state and test timestamp. It uses `Cache-Control: no-store`. PUT accepts exactly provider/key/expected revision; POST tests exactly provider/revision; DELETE accepts exactly provider/revision. Origin checks compare the browser Origin to the configured auth origin and reject cross-site writes. No method accepts a client owner ID. Bodies are bounded before parsing; keys are 32–512 visible ASCII characters without whitespace. A new record requires revision null; replacement/deletion requires the current UUID revision. A stale device receives a conflict rather than overwriting a newer key.

`provider_credential` has one row per owner/provider, a cascading Better Auth user FK, RLS enabled, and revoked public/anon/authenticated role privileges. AES-256-GCM encryption uses a fresh random 96-bit nonce, 128-bit tag and a canonical base64 256-bit secret loaded only in server modules. Associated data binds the algorithm/domain, owner, provider, key version and credential revision. Moving ciphertext between owners/providers/revisions, tampering, malformed data and missing/retired versions fail closed. Plaintext is never returned, included in exports, persisted in the database or logged. The form necessarily holds the user-entered key transiently until save/unmount; it uses a password field and no local/session storage.

Account export selects safe credential metadata and resource operation metadata explicitly; it does not select ciphertext, nonce, key version, key material or provider response bodies. Account deletion cascades owned keys, sessions, chats and personal records, while anonymous service resource leases intentionally survive deletion. Account deletion, key deletion/replacement and provider entry share the same advisory transaction lock, so deletion before entry prevents use; a committed entry may continue after deletion. Export derives the actor from the authenticated owner and selects safe lease metadata, never the opaque actor key. If the resource secret is absent, lease metadata is unavailable rather than attributed to an invented owner. Deleting or replacing a key prevents later entry with its old revision. Requests that have already entered the provider cannot be recalled remotely by deleting a local record; Stop uses the request abort signal and uncertain work remains subject to recovery.

## Explicit funding, models and third parties

Every chat POST requires `funding: platform | openrouter | gateway`. The latter two mean the signed-in user's saved key for that provider. Unknown/absent funding is rejected. BYOK execution never reads platform provider keys, prices or the credit store; it creates no dollar reservation or ledger event. A provider rejection, missing key, unavailable encryption, catalog rejection or resource limit never substitutes platform money or another provider. The platform path retains F06's verified BASIC allowlist, integer microdollar reservations, daily/shared caps, kill switches and conservative unknown-cost settlement unchanged.

`BYOK_ENABLED=0`, blank encryption configuration and blank catalog keep inference disabled. The server catalog accepts at most 100 unique operator entries with explicit ID/name/adapter/model/provider, `verified: true`, an unexpired timestamp, and strict text/reasoning/sources/files/tools/search capabilities. Only text routes with files/tools/search false are accepted in this slice. Unknown parameters are rejected; clients cannot send provider options, arbitrary model identifiers, URLs or provider credentials in a chat request. No model name, price or universal capability is guessed. The operator must verify the specific static model/host route and limits before setting verified; an automatic router or virtual model is not evidence of a verified single-model route. Future catalog expansion can add reviewed entries without exposing arbitrary client parameters. This is a supported catalog, not a claim that every provider model or modality works.

Both adapters receive an explicit SDK model, the selected user key, one operator-selected provider host, 512 maximum output tokens, no SDK retry and a 20-second server timeout combined with the request abort signal. OpenRouter disables fallbacks and requires parameter support; nonreasoning routes explicitly disable reasoning, while reviewed reasoning routes receive a 128-token reasoning budget inside the output cap. Gateway receives only the selected host and no fallback model list. Gateway reasoning/sources render only if supplied and declared; no source/reasoning text is manufactured. Raw provider diagnostics, warning messages and provider metadata are discarded at installed SDK middleware boundaries before the SDK's default logger or UI stream can expose them. HTTP auth failures mark only the current matching key revision invalid and expose a stable error ID. A late response for a replaced key cannot alter the replacement or another owner.

Settings and composer disclose that the user's selected provider account pays its own charges, messages go to that provider and its selected model host, while the key authenticates the provider under its terms, platform model credits are not deducted, model permissions may vary and service limits still apply. The app's limits do not bound the user's provider account balance or guarantee a maximum provider bill; provider-side spending limits remain the user's responsibility.

## Authentication testing without inference

“Test key” makes exactly one authenticated GET to a fixed metadata endpoint: `https://openrouter.ai/api/v1/key` or `https://ai-gateway.vercel.sh/v1/credits`. It never invokes `generateText`, `streamText`, a generation lookup that first creates a generation, or a model-list endpoint that may be public. Redirects are rejected, the response has an eight-second timeout and a 16,384-byte JSON bound, and provider details are discarded. Auth success means recognized metadata from an authenticated endpoint, not proof of access to every model, funding, inference quality or future validity. OpenRouter management/provisioning/disabled/expired credentials are rejected when the endpoint identifies them. Gateway accepts its documented string balance/total_used shape. 401/403 becomes invalid; malformed, unavailable or oversized responses become unavailable. Test timestamps and states are owner/revision scoped. Tests count against service resources.

Primary references inspected: [OpenRouter current-key metadata](https://openrouter.ai/docs/api/api-reference/api-keys/get-current-api-key), [Gateway generation/credit metadata APIs](https://vercel.com/docs/ai-gateway/observability-and-spend/usage), [Gateway authentication](https://vercel.com/docs/ai-gateway/authentication-and-byok), installed `@ai-sdk/gateway/src/gateway-fetch-metadata.ts` for the authenticated `/v1/credits` shape, installed Gateway provider options, OpenRouter v4 provider types, AI SDK 7 stream/UI/middleware/logger source and version-matched docs, and Next 16's installed route handler guide. Only documentation was fetched remotely. Metadata auth endpoints perform no inference; actual account behavior remains a live check.

## Durable resource policy and chat lifecycle

BYOK has its own SQL resource leases and advisory transaction lock (`41021407`), separate from F06 money locking/rows. The existing `byok_operation` table stores a domain-separated HMAC actor key under an explicit stable `BYOK_RESOURCE_SECRET`, with no user FK, raw user ID, prompt, ciphertext, nonce, masked key or provider secret. Request digests are also domain-separated HMACs rather than unkeyed prompt hashes. Retained provider identifiers, random revisions/run IDs, state and timestamps are resource metadata. This pseudonymous retention is disclosed and keeps global/actor limits from resetting when an account is deleted. Completed runtime work can still settle its matching lease after personal records are gone. Old operations cannot resolve deleted credentials. Current policy: one active operation per account, eight globally, 30 attempts per UTC hour/account, 200 per UTC day/account, 5,000 per UTC day globally, and hard retained-record ceilings of 10,000/account and 100,000 globally. Counts include rejected-after-reservation, aborted, completed and test operations. Retention ceilings intentionally pause new work until a deliberate operator retention decision; no automatic removal resets idempotency or active holds. Text input/context uses the existing bounded recent-12-turn, 12,000-byte context policy with no paid summary. Keys are limited to two bounded encrypted records per account.

Operations reserve before decrypting and commit `entered` before SDK invocation. Entry rechecks enablement, owner/provider/revision and invalid-key state under the same lock used by replacement/deletion. Only a request that never entered releases its reservation. For generation operations, a complete provider terminal response or explicit auth rejection completes the resource lease; network failures, interrupted streams, cancellation and missing terminal outcomes retain a held slot. Non-inference metadata GET tests always complete their resource slot when the bounded attempt returns or aborts, including unavailable/invalid outcomes: they cannot leave remote inference running. A process crash during either kind still leaves its durable reservation/entry active, and no timer retries or expires it. Operator recovery must establish that remote work has ended before calling the server-only store's terminal finish path (while the owner ID is still known) or making an equivalent audited SQL correction; only a provably unentered reserved record can release before entry. For deleted accounts whose raw ID is no longer available, an authorized operator must match the opaque lease ID/actor and document remote terminal evidence before updating it; do not invent a new user mapping. These are resource holds, never platform money events. Investigate remote activity first; deleting a key does not settle a hold.

The F05 owner-scoped run claim, request digest (including funding), UUIDs, original-preserving send/edit/regenerate/retry behavior, bounded branch snapshots and independent SSE persistence are shared by both modes. Both user and assistant slots are reserved before saving a run or calling a provider. Duplicate or changed-content IDs cannot invoke a second provider. Client disconnect drains independently; stop persists partial text and a stopped run. Missing terminal completion stays an error. Accepted-only draft clearing and the existing reduced-motion/focus contracts are preserved.

## Rotation and secret operations

Keep encryption keys in the host's server secret manager, separate from the database, backups, browser env and platform provider keys. `BYOK_RESOURCE_SECRET` is an independent stable HMAC secret of at least 32 characters, shared by all instances; retain it while any lease is unresolved and do not rotate it with encryption keys. Changing it would change actor attribution and owner exports. Rotate it only through an explicitly reviewed migration of all live/retained actors, preserving global/actor counts and unresolved holds; the encryption rotation below does not change it. `.env.example` intentionally contains blank encryption material and enables nothing. A keyring is a JSON map of at most 16 version IDs to canonical base64 strings representing 32 cryptographically random bytes; the active version must exist. Never reuse a version ID for different bytes.

1. Generate a new independent 256-bit key in a secure operator environment. Add a new version to the secret manager while retaining every version still referenced by stored rows. Deploy this expanded ring to all server instances before writing with it.
2. Switch `BYOK_ACTIVE_KEY_VERSION` to the new version on all instances. New/replaced credentials now use it; older credentials remain readable through their own metadata.
3. In an authorized server-only maintenance runner, select owner/provider metadata only and call `new ByokStore(db).rotate(userId, provider, process.env)` for each record. The method locks and rereads the current owned row, authenticates the old ciphertext and writes fresh nonce/ciphertext under the active version while preserving the revision. It returns no plaintext and is safe against concurrent replacement/deletion: retry an owner/provider that changed or disappeared rather than applying a stale snapshot. Do not log arguments containing secrets or dump rows. Keep batch size bounded and record counts/version IDs only.
4. Verify that every remaining credential's key_version matches an accepted version and no row references the retiring version. Confirm every running instance can decrypt the new version. Retain old material as required for encrypted backup recovery; do not delete it merely because the live database is migrated.
5. Remove the retired version only after the live and backup recovery plan permits it. Missing versions fail closed; they do not substitute a platform key or silently destroy a stored row. If a key is suspected exposed, disable BYOK, replace affected provider credentials at the provider and locally, rotate encryption material, investigate access and restore service deliberately.

Encryption protects database-only disclosure and tampering. It cannot protect against a compromised application host/secret manager, a provider receiving an authorized key, client malware reading an entered key, provider retention/billing policies or loss of all secret versions. Use host log/trace redaction and secret access controls; no telemetry integration was added here. Real Workers runtime cryptography, shared PostgreSQL backends/pooler concurrency and secret-manager rollout remain deployment gates.

## Disconnect fixture diagnosis and correction

A subsequent independent root run found a separate sequential failure: 84 passed/1 failed, with `chat_persistence_failed` and one saved user message where the disconnect regression expected user plus assistant. It completed in 1.71 seconds, so this was an actual assertion/persistence error, not the previously observed five-second concurrent-load timeout. Increasing its polling or timeout would not repair a failed SQL transaction.

The original `bun test tests/f07.integration.test.ts --test-name-pattern 'F07 BYOK disconnect' --rerun-each=15` reproduced three failures in 15 runs. Temporary instrumentation recorded only error names, SQL error codes and a narrowly matched numeric bind-count signature. A subsequent five-run baseline reproduced three exact missing-assistant failures and captured PostgreSQL **08P01: `bind message supplies 3 parameters, but prepared statement "" requires 0`**. No SQL values, credentials, auth headers or provider bodies were logged.

The fixture's `operations()` poll used PGlite's direct query API while the independent resource/persistence consumers used the application's postgres.js socket. PGlite has one backend session: direct API access replaced the socket transaction's unnamed prepared statement between protocol Parse/Bind messages. A single postgres.js connection limits its own callers, not direct engine callers. This explains both resource completion failures and a failed assistant persistence transaction; waiting longer cannot recover that transaction.

Changing only the operation poll to the captured application Drizzle connection made all 15 repetitions pass. The final fixture sends every post-start SQL seed/read/assertion through that same postgres.js `max: 1` queue, retaining real SQL, the PostgreSQL wire protocol, the existing assertion and the original 100 × 5ms poll bounds. No production persistence, SSE draining, provider, financial/resource hold, cancellation or deadline behavior changed. Temporary production diagnostics were removed and both production files compared byte-for-byte against their pre-diagnostic backups.

Final targeted verification: the unchanged disconnect/stop/truncation regression passed **20/20 repetitions, 180 assertions, 21.20 seconds** with Bun's default five-second deadline. The complete F07 file then passed twice: **36 tests, 552 assertions, 35.58 seconds**. The final isolated complete suite passed **85 tests, 702 assertions, 47.02 seconds**, including all prior F03/F04/F05/F06 cases. Lint, standalone typecheck, vendor integrity and whitespace checks passed after the fixture change; the prior credential-free production build remains applicable because production source was unchanged. The existing handler-level disconnect assertion remains the regression at the real seam; it was observed red before the fixture correction and green afterwards. All temporary diagnostic code is removed.
