## Provider, catalog and funding boundaries

`FUNDED_ADAPTER=openrouter` is an explicit required server setting. A blank/unknown adapter fails closed; the SDK always receives an explicit model object. `openRouterProvider` and `gatewayProvider` use the installed SDK/provider factories with retries disabled and exactly one operator-selected endpoint. Gateway has an explicit server API key and provider `only` routing, but `resolveFundingConfig` rejects funded Gateway with `gateway_receipts_unverified`. Its usage shape is different from OpenRouter's raw cost receipt; no Gateway receipt is interpreted as a free/known bill. Gateway funding requires separately verified prices, endpoint bounds and settlement semantics before activation. There is no implicit routing, paid fallback, first-token title call or hidden auxiliary inference.

The server model catalog exposes only the configured, unexpired BASIC text-only OpenRouter price snapshot's model and capabilities. No model names/prices are guessed. The expired/unknown-price, unconfigured and disabled states return no selectable model. `/api/credits` remains authenticated, identity-derived and `no-store`, and adds `models` to its existing contract. The real UI and sidebar consume this response together: daily remaining credits never override disabled, daily/shared exhaustion or busy states. A busy view says “Request in progress”; it refreshes while busy and on window focus/request completion. Failed access reads close generation. The server remains authoritative if a displayed balance becomes stale. BYOK entry/storage/inference is still F07; guests and their bot/proxy constraints were untouched.

F06's integer microdollar reservations, actor/day and shared/monthly ceilings, immutable ledger, pre-entry release rules, exact receipt validation, conservative unknown holds and kill switches are preserved. An entered cancellation never proves zero cost. The client request signal is combined with the bounded server timeout; billing drains independently. Provider errors, truncated answers and cancellations retain unknown holds unless a complete validated receipt exists. A moderated answer with a complete receipt still settles its actual cost. Gateway's unsupported receipt shape never releases such a hold.

## Durable branch and transport contract

Migration `0003_chat_branches` adds owner-scoped branch snapshots and run claims, with cascading chat/account deletion, RLS and revoked browser-role privileges. Original messages retain their IDs and parts. The initial migration builds each original snapshot with SQL `ORDER BY created_at,id`, preserving sub-millisecond order without converting cursor timestamps through JavaScript. Existing message/history cursor logic is unchanged. Branch snapshots deliberately copy bounded UI message arrays: this small persistence seam preserves originals and reliable display order without recursive parent traversal.

Each POST accepts strict UUID `id`, `branchId`, `requestId`, a fresh UUID user message, allowlisted `model`, and `action: send|edit|regenerate|retry`; fork actions also require an owned `anchorId`. The real UI now uses UUIDs throughout, correcting the inherited nanoid/UUID mismatch. Funding is explicit platform/private text only; search/files/unknown extra fields are rejected. Clients cannot supply owner identity or trusted history/context. The server derives context from its owned snapshot.

An owner-safe transaction locks the chat, verifies its source branch/anchor, saves the new prompt and claims the unique request ID. Normal send appends to the chosen branch. Edit forks the prefix before the edited user prompt; regenerate/retry forks before the relevant user prompt and copies that prompt to a fresh message. Originals are never deleted or overwritten by these actions. Run IDs reject exact duplicates and changed-content conflicts with 409 before another provider call. A second pending run on a chat is rejected. A deliberate retry has its own request ID and branch and is subject to existing financial holds/concurrency. There is no automatic replay or automatic paid retry.

The stream returns `x-chat-branch`; the UI tracks the branch, reloads saved messages, and exposes a labeled native branch selector, saved reload, and explicit retry-in-new-branch. Server `GET /api/branches?chatId=...&branchId=...` derives ownership and returns branch choices, selected messages and run state with `no-store`. It returns no cross-owner content. Export includes owned branch snapshots and run metadata, and account/chat deletion cascades the new records.

The AI SDK SSE response has an independent consumer so response-body cancellation alone does not stop persistence. On end, one transaction appends at most one assistant and records `complete`, `error` or `stopped`. Complete requires a stop/length terminal event; partial text without a valid terminal completion stays an error. Stopped partial text remains visible. Terminal writes are idempotent and owner scoped. Request abort before provider entry releases only its unentered reservation and records stopped; abort after entry keeps uncertain spend. Live host termination can interrupt best-effort drains: durable pending runs and financial holds remain, block duplicate inference and require operator investigation/reconciliation. No timer releases unknown incurred spend or silently reruns a pending request.

## UI and bounds

The real shell fetches the catalog and credit state, restores branches on reload, and enables stop/edit/regenerate/retry only through these server contracts. Edit is labeled “Edit in a new branch”, discloses original preservation, focuses its text area, and returns focus on Escape/cancel. The branch selector and text input retain mobile 16px text and semantic focus tokens. Branch changes clear an unrelated transport error; saved failed/stopped/pending runs remain explicitly labeled. Copy and existing safe Markdown/code rendering remain available. Existing source/reasoning components render supplied stored parts only; this funded BASIC nonreasoning route does not request reasoning/search or manufacture citation/reasoning output. Broader provider capabilities require separately verified catalog/funding support.

Input is bounded to 2,000 characters per text part, eight parts/request and a 12,000-byte serialized context. Context keeps at most 12 recent text turns, dropping oldest first; output is capped at 512 tokens. No paid summarization exists. Branch snapshots are bounded to 500 messages and 100 branches per chat; further sends/forks require a new conversation. Titles use local bounded whitespace-normalized prompt text inside persistence and never await another model.

The existing development-plus-flag-only `/preview/ui` harness adds a `branches` scenario with shared branch navigation and local fixture callbacks for edit/regenerate/selection. Example: `/preview/ui?canvas=1&state=branches&credit=available`. It sends no auth/database/provider requests and creates no production bypass. Fixture credits/model responses are labeled. ## Independent review corrections

Root's two-axis review identified three actionable issues. Draft clearing previously happened before a submit callback could decline during saved-history synchronization. The composer now requires an explicit accepted claim, disables Send during reload/submission, guards same-tick duplicates with a ref, and preserves a draft on rejected claims; an already-open editor also retains its draft on a rejected claim. A shared-behavior/render regression exercises blocked reload, accepted submission, a concurrent rejected claim and visible disabled Send without source-string checks.

The 500-message cap previously considered existing messages alone. The server now computes the selected action's prefix first and reserves both user and assistant slots before saving a run or calling a provider. A real-handler regression seeds a failed user-only 499-message branch: a new send is rejected with zero provider calls and no run/message growth, regeneration at its final user creates a valid 500-message branch, an earlier edit creates 498 messages, and the 499-message original stays intact.

The editor now keeps the stable “Send as new branch” label with `aria-busy`, a spinner and its duplicate-action guard. Root owns independent re-review of these corrections. No self-grade was assigned.

The parent's test-only F06 correction was applied without changing Git state, preserving F05's explicit adapter fixture and migration expectation. F05's three socket-backed rejection checks also use its native-await `rejectionOf` helper; its 30-second override was removed and its fixture socket matches the application's single connection. Focused F05 verification passed 13 tests/91 assertions in 2.15 seconds under the default five-second per-test deadline. The final combined suite above includes these changes. Final lint, types, integrity, whitespace and credential-free production build all passed after the corrections.
