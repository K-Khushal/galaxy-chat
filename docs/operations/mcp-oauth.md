# Local OAuth state and encrypted credentials

This is an offline persistence slice. Production binding issuance, PKCE preparation/consumption, grant installation, secret access, rotation and refresh entry are permanently unavailable (`mcp_oauth_authority_unavailable`). No flag enables them. There are no HTTP routes, UI, discovery, authorization navigation, token exchanges, provider calls, broker dispatch, OAuth client registration or real credentials. The fixture factory requires `NODE_ENV=test` at construction and every authority/secret operation, including final validation after awaited writes. Fixtures declare synthetic untrusted manifests, not provider authenticity or actual endpoint/cost evidence.

The original registry owns one connection bound to one exact MCP purpose. That ownership does not authorize OAuth. `mcp_oauth_binding` explicitly binds a server-authenticated owner and current connection revision/profile digest to exactly one of the five OAuth purposes, a complete application profile identity, and an immutable manifest. The manifest also includes broker and upstream endpoints, authorization endpoint, issuer/resource, client, exact redirect URI, ordered bounded scopes, form fields and expiry; these fields are absent from the original application profile digest. No discovery response or token can add endpoints. Local validation rejects noncanonical HTTPS URLs, literal IPs, credentials, fragments and queries. It does not perform DNS or prove the destination; those are separate broker/hosted gates. The same MCP connection cannot imply permission for token/refresh/revoke or another OAuth purpose.

PKCE preparation generates cryptographic random state and verifier, an S256 challenge and at most ten-minute database-clock expiry. State and authenticated session identifiers are stored only as hashes; the verifier is encrypted. Consuming requires the exact owned active session, redirect, current invitation, connection, profile and manifest. It atomically consumes the state and destroys persisted verifier material. A committed consumption is not replayable after a crash and is not authorization to exchange a code. Synthetic grant installation additionally requires that exact consumed state and session. Better Auth GitHub state and broker request nonces are not reused for MCP CSRF. Future HTTP initiation must enforce authenticated same-origin CSRF checks; callback processing must validate session-bound state and exact redirect rather than trusting arbitrary query endpoints or requiring a cross-origin redirect's Origin header.

Access and refresh values are bounded to 8 KiB each, encrypted with AES-256-GCM, a random 96-bit nonce and a dedicated versioned MCP AAD domain. AAD binds owner, connection/revision, grant or PKCE identity, full profile/manifest digests, credential revision, token kind and key version. The required runtime keyring has at most eight explicit 32-byte keys; missing historical keys, bad AAD or tampering deny secret access. Grant expiry conservatively bounds all secret use, including refresh; no unknown refresh lifetime is assumed. Rotation requires the old key and a current revision, reseals with a new credential revision and preserves grant identity. Metadata database errors use the same fixed scrubbed error mapping as transactions and require no admission runtime or keys. Metadata/account exports contain only grant identity, binding identity, revision, local state, expiry and refresh presence. They contain no token, ciphertext, PKCE/state/session hash, URL or key material.

All writes use READ COMMITTED and existing BYOK advisory lock 41021407. A future funded transaction must first hold funding lock 41021406; this module never acquires it or calls funding from a BYOK-held callback. Final validation samples current DB wall time and owned binding state, then synchronously rereads authoritative runtime profiles/manifests, current invitation, and optional session after all preceding awaits. Refresh operations validate both the original token binding and the exact refresh binding in their final observation. Runtime or identity drift rolls back all writes.

A refresh claim receives a monotonic persisted fence and binds the credential revision produced by reservation. Only one reserved/entered/unknown claim may exist for a grant. Entry commits once before any future token use; a crash after entry cannot replay. Replacement atomically commits both new access/refresh values and marks the claim replaced once. No network outcome is simulated as authentic. Only durable reserved state permits cancellation. Expired/failed entered claims retain uncertainty; `retainRefreshUnknown` blocks both old refresh and access use, and no automatic lease stealing or refresh-token retry exists. Claims remain blocking after expiry until explicit local cleanup. Rotation refuses active claims. Local revocation invalidates states/claims and destroys credential material; it means local revocation only, never successful remote revocation.

Per connection there is at most one configured binding per OAuth purpose, one pending token PKCE state, and one active/uncertain grant. Scopes are limited to ten bounded names; runtime manifests to 32 and manifest JSON to 16 KiB. Every admitted binding/state/grant/refresh consumes a retained anonymous domain-separated HMAC counter of the canonical GitHub account id from exactly one trusted Better Auth `account` row (`provider_id=github`): at most 100 owner/1,000 global lifetime records and 10 owner/50 global UTC-day admissions. Unknown markers are bounded by admitted refresh claims. A missing, ambiguous or noncanonical numeric GitHub account binding denies admission. Mutable login labels and local user ids are excluded; deleting and re-creating the same GitHub account under a new user id cannot reset its owner counters. The owned account/user rows are locked for the admission transaction. Deletion cannot reset these counters; changing their independent counter secret fails closed against its stored fingerprint. No counter-key retirement/reset is implemented. Secret-bearing metadata may cascade on owner/connection deletion; deletion of an entered/unknown refresh creates or preserves an anonymous uncertainty marker. These markers are not billing receipts or proof of financial termination. Existing operations, receipts, carry and other financial tables are untouched.

Tests use actual migrations and the captured application SQL driver over queued PGlite, with barriers after real queries. This proves local state/rollback/persistence, not native PostgreSQL multi-backend contention, issuer authenticity, funding, token rotation at a provider, endpoint safety, dispatch or hosted recovery.

Local cleanup remains available without new admission or secret keys. No account login, provider selection, provisioning or paid request is part of this implementation.
