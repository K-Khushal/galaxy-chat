# Durable jobs: local fixture slice (F14-B)

This is an offline engine slice, not completion of ticket #36 or proof of hosted delivery. There are no HTTP job routes, UI, deployed worker, cron, queue activation, OAuth, connectors, model calls, or arbitrary commands. The only adapter is `local-fixture-v1`, which measures one exact immutable owned F11 artifact revision and proposes a Markdown report of byte/character counts and a source digest. Source content is untrusted data and is never interpreted as instructions. The report clearly says that it is deterministic and not model generated.

`JobStore.enqueue` accepts a caller's authenticated owner id plus a UUID request id and exact artifact revision. A future HTTP entry point must derive the owner from `requireChatAccess`, enforce same-origin and request size, and never accept an owner id or history from the client. The store independently locks the user and checks the current GitHub invite allowlist. Guest, missing, temporary-chat, revoked-invite and other-owner inputs cannot enqueue/approve/read a job. Cancellation is available internally after invite removal to stop owned local work. IDs never authorize ownership. Internal account exports use their existing account-access checks and include owner-filtered safe job metadata/proposals and result references, without introducing a new invite requirement for data export; account deletion cascades job records and attempts.

Enqueue does not start work or an HTTP background promise. A host adapter must persist a delivery containing only a job id after enqueue and redeliver after failure. Expired running and approval-waiting jobs are delivered before queued jobs, so a bounded oldest-queue prefix cannot hide the leases that occupy the active slots. Storage is the source of truth: `pendingDeliveryIds` supplies queued, lease-expired and approval-expired ids, so a lost enqueue notification is recoverable. The offline worker harness is available only when `NODE_ENV=test`; every invocation rechecks this gate. Production delivery remains disabled until a funded host/queue, recurring recovery schedule, fees, database connection behavior, deployment and recovery proof have been reviewed. Environment flags cannot enable this fixture worker in production.

One active job per owner and two globally; ten queued per owner; 200 records per owner and 2,000 globally (F13 bounds). Running and approval-waiting jobs count as active, including expired leases until fenced recovery. All attempts and continuations share five attempts and ten minutes from first execution. Each attempt has the tighter F13 twenty-second lease; source/output are bounded by F11/F13. There is no lease renewal. The fixture has two durable steps: measure/propose, then publish the approved proposal. Queue retries increment the same persisted attempt count. No retry resets the wall clock or approval expiration. Record limits fail closed; no silent retention deletion exists.

A delivery claims a fenced SQL lease and records an attempt before work. Duplicate deliveries during a valid lease are no-ops. Worker loss before checkpoint leaves an entered attempt; after expiration a new delivery marks it expired and increments the fence. Every checkpoint verifies ownership, current state, fence, attempt and checkpoint. Database wall time is evaluated in the final conditional update after awaited artifact work. F11 output creation and completed checkpoint commit in one transaction: a crash rolls back both or commits both. Replaying completed work creates no extra artifact. Local attempts are safe to repeat; no nonidempotent external action adapter exists, and adding one requires an explicit uncertain outcome state and reconciliation instead of automatic replay.

Approval is for `publish-fixture-report-v1` plus the exact persisted SHA-256 checkpoint digest, including job/source revision and full proposal. It expires after five minutes and cannot be extended by replay or retry. The persisted action revision and proposal/source identity are immutable in SQL; content changes require a new job and approval. A newer artifact head does not change the selected immutable revision. Missing/deleted source denies publication. Expired waiting approvals fail on the recovery sweep. Cancellation increments the fence; post-cancel checkpoint writes fail. Job cancellation, lease expiry or account deletion is not proof that remote work stopped. This local adapter starts no remote work and never modifies credit, budget, BYOK, image or tool financial/resource holds. Existing anonymous financial records remain governed by their original reconciliation rules.

All job transactions explicitly use read committed isolation so advisory-lock waiters do not reuse a snapshot pinned before the lock. The SQL session-default probe verifies this override; PGlite cannot establish real concurrent backend contention, which remains a native PostgreSQL gate. Lock order is existing BYOK resource lock, attachment lock, jobs advisory lock, then owner and job rows. F11 publication uses the same transaction and lock ordering. Browser roles have no job-table privileges and RLS is enabled. Persisted job state contains only owned source identifiers, bounded deterministic proposals, exact approval digests, safe fixed error ids, attempts and result references. No credentials, provider payloads, arbitrary tool output, stack traces or raw source copies are recorded.

Still pending: job start/approval HTTP controls and any UI for creating work; host/queue delivery and crash/restart evidence across real processes; queue/host pricing, aggregate funding integration and fees; live runtime database/restore/recovery proof; connector #35 and approvals for any future external action; accounting and uncertain remote reconciliation for any future provider. No live/provider/OAuth/cloud acceptance is claimed by the SQL and fake delivery tests.

An authenticated status surface (F14 status slice, issue #52) exists without enabling delivery: `GET /api/jobs` lists owned jobs and `GET /api/jobs?id=` reads one; `POST /api/jobs` with `{action:"cancel",id}` cancels an owned job. Ownership is derived from `requireChatAccess` (guest and temporary access are rejected upstream), foreign or malformed ids return 404, mutations require same-origin and bounded strict-schema JSON, and every response is private/no-store with error bodies carrying only fixed error ids. The `/chat/jobs` page shows stored state, attempts, the exact source artifact id and version as plain identity (no revision-pinned download: the artifacts API serves current head content), the action revision, the proposal as plain text, approval expiry and, for completed jobs, a download of the owned result artifact. Start, create and approve controls are intentionally absent with an explanation that production worker delivery is not configured. Cancellation prevents future attempts only; the confirmation dialog states it does not guarantee in-flight work terminated and implies no refund, keeps failure feedback and retry controls inside the dialog, and returns focus to the row that opened it after Keep, Escape and successful cancellation (the row's Details control when its Cancel button becomes terminal and disappears). After a successful cancellation the client awaits a fresh authoritative list; list and detail responses that were already in flight before the cancel began are discarded so an older response cannot revert a cancellation in the UI. The page polls at most every ten seconds and only while a queued, running or approval-waiting job exists and the tab is visible; in-flight list/detail reads carry bounded timeouts and are aborted on unmount, hidden tabs and supersession without those intentional aborts being shown as errors.

Offline proof includes duplicate delivery and worker replacement, stale fences, persisted crash recovery, real SQL artifact-insert lease expiry with transaction rollback, exact/expired approval, owner/invite denial, queue and active caps, five-attempt exhaustion, source/account deletion with exact financial holds and ledger preserved, and physical snapshot restore into a fresh PGlite runtime with all network dispatch denied. This is local proof only.
