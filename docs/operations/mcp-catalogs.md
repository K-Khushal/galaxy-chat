# Owned MCP catalogs and action approvals — offline persistence

This slice stores explicitly untrusted catalog metadata and exact action proposals. Production catalog import, proposal admission and action verification return `mcp_catalog_authority_unavailable`. There is no discovery client, route, model tool, OAuth issuer, real fee issuer, ledger activation or transport dispatch. The existing production operation authority remains unavailable. Fixture model estimates and MCP fees are synthetic accounting inputs, not actual prices or cost guarantees.

Only a current invited owner with one exact configured `mcp.call` connection and the complete current canonical profile digest can import call actions. `mcp.list`, connection consent and annotations never authorize calls. Descriptions and the four supported annotation hints are untrusted data and never become model instructions. Unknown catalog fields, credentials, tokens, endpoint fields and executable schema extensions are rejected; connection resource/issuer URLs are represented by profile identity and digest rather than copied into metadata.

Catalog revisions, action/schema definitions and proposal bindings are immutable. Separate owner/head/revocation metadata uses CAS. Exact current import replay is idempotent; changed content for the same revision, stale head CAS, old-head resurrection and revoked imports fail. Head changes revoke pending/approved actions. Connection deletion, disable, revision change, changed profiles, missing invitations and authoritative configuration drift invalidate verification. Owner or connection deletion cascades metadata, while anonymous admission counters survive. Catalog code has no financial ledger references or deletion/release procedure.

The schema policy accepts root objects with explicit `additionalProperties:false`, named properties and unique required lists; bounded arrays; strings and unique string enums; finite bounded numbers/integers; booleans and null. Optional output schemas use the same policy. Unknown keywords, references, patterns/regex execution, combinators, formats, defaults and executable extensions are rejected. `minLength`/`maxLength` count Unicode code points, with independent UTF-8 byte ceilings. Bounds are 8,192 bytes/schema, depth 5, 64 schema nodes, 16 properties/object, 16 items/array, 1,024 bytes/string, 4,096 total argument bytes and 2,048 validation operations. Arguments are detached and frozen before the owned schema lookup, then checked exactly against the accepted schema. Catalogs contain at most ten unique tools and 65,536 bytes of canonical definitions.

Lifetime retained admission bounds are 20 catalog revisions/owner, 200 globally, 100 proposals/owner and 1,000 globally. Anonymous counters derive from the existing server BYOK resource actor and cannot be supplied by the caller, updated or deleted. Removing metadata cannot recover these counters; server resource-secret rotation is not a user operation. Existing ToolStore limits remain tighter where applicable: four calls/approvals per run and approval expiry no later than run creation plus 20 seconds. There is no independent five-minute MCP approval window.

Proposals require a real owned running `tool_run`, queued/running owned `tool_call`, entered BYOK operation and the current matching credential. Bindings cover exact run/call and reviewed run-request/model digest, detached arguments and target, connection/profile, catalog revision, complete action/input/output-schema digests, fee snapshot digest and shared plan/capacity identity. Every call requires an explicit owned ToolStore approval, including `readOnlyHint:true`. Existing approval rows carry the decision; an immutable proposal extension records its full binding and approval digest/revision. Changed bindings, denied/revoked/consumed states and expired runs cannot consume again.

`issueToolApprovalInTx`, `decideToolApprovalInTx` and `consumeToolApprovalInTx` reuse the existing approval machinery without nested transactions. `verifyMcpActionInTx` reads exact persisted ownership and binding state; it accepts no caller-created verified object or boolean callback. All new mutations are READ COMMITTED under the existing BYOK lock. A future operation-entry caller must first hold funding 41021406, then BYOK 41021407, and consume in that same transaction. No current operation-entry integration exists. Final SQL observations include DB wall time and current owner/connection/head/run/approval/plan state; after the last await, authoritative environment and fixture fee configuration are resolved again. Late drift rolls back writes and approval consumption.

Only the fixture factory can register configuration for its active test transaction; construction and authority-dependent operations require `NODE_ENV=test`. A normal ToolStore caller or production factory cannot create this context. Offline tests construct synthetic runs through actual ToolStore/ByokStore SQL transitions without provider execution. Their queued PGlite evidence covers persistence, rollback and guards, not independent PostgreSQL backend contention, actual catalog provenance, real fees or live execution. Real issuer/catalog ownership, a production MCP-owned execution contract, pricing, receipts, funded hosting and native PostgreSQL contention remain launch gates. Account catalog exports contain owned IDs, revisions, state and creation time only.
