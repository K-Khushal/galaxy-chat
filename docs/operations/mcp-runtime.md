# Credential-free funded MCP runtime

This internal backend service has no HTTP route, UI, automatic model tool registration, discovery, OAuth or deployment activation. `createMcpRuntime` works with complete reviewed operator configuration and remains off by default. Fixture tests use the production path with synthetic metadata/prices, generated signing keys, actual SQL and the actual broker with an offline TLS destination. These tests are not evidence of real server ownership, prices, billing or hosted behavior.

Operator configuration in `MCP_RUNTIME_CONFIG_JSON` is a strict expiring manifest: ID/revision/review timestamps and proof reference/digest; canonical broker endpoint; Ed25519 verification public key/version; explicit synchronous/stateless/credential-none declarations; separate complete initialize/call profiles; one read-only operator-allowlisted tool/input/output schema; and three independently reviewed all-in fee/capacity snapshots (initialize, initialized notification, call). Actual values and evidence must be supplied by the operator; this repository chooses no provider or price. Every fee is positive and binds the active plan's shared capacity. Reviewed response-byte and wall-time bounds must match the enforced profile limits; actual request bytes are checked against each frame's admitted request limit. `MCP_RUNTIME_ENABLED=1` alone never grants authority. Existing client mTLS/HMAC configuration and funded plan/carry must also be valid. Private evidence signing keys exist only at the broker; the app receives public keys.

Call `adoptRuntimeManifest` as a verified current invited server caller, passing separately owned existing `mcp.initialize` and `mcp.call` connection identities and the exact manifest digest. Explicit initialize consent covers precisely initialize and notifications/initialized, each separately approved and funded. Adoption imports the one reviewed tool into the owned immutable catalog; configuration/adoption never authorizes execution. Existing registry purpose enum and five-connection cap remain unchanged.

`prepareRuntimeExecution` requires the actual owned running ToolStore/BYOK run and queued tool call. It freezes exactly three frame bodies and creates three ToolStore approvals. Two setup call slots plus the supplied call consume the existing four-call budget, and every immutable frame expires at the earliest of original run-created+20s, execution preparation+reviewed frame wall-time, and manifest/fee expiry. Approval and dispatch never renew that deadline; short profiles can execute immediately without waiting for the original run window to shrink. `decideRuntimeApproval` records each explicit approve/deny/revoke decision. Read-only annotations never bypass approval. Original entered BYOK request/model/provider/price digest and current credential are checked again after awaits. Stable GitHub numeric account IDs from exactly one trusted auth account binding govern retained admission limits. Runtime financial actor mappings separately survive account deletion and configured actor-key rotation; legacy actors are unchanged. The first runtime admission pins the stable principal secret fingerprint; the first financial entry pins a domain-separated canonical GitHub account principal to its actor-key version. New user IDs and later active actor-key versions keep that original actor and all lifetime/day totals. The original actor key must remain in the bounded keyring: removing or changing it denies new entry. A retained fingerprint also rejects changing BYOK_RESOURCE_SECRET; that stable principal secret requires an explicit separately reviewed migration, never a counter reset. Neither account deletion nor key rotation deletes retained financial identity.

`bootstrapMcpPeriod` is an internal operator procedure: it derives durable carry sources inside SQL transactions and verifies the actual reviewed plan, accepting no caller-invented source amounts. `executeRuntime` atomically reserves each frame's fee/resources, consumes its exact approval, and commits one-attempt entry under funding lock41021406 then BYOK41021407 before dispatch. Production authority comes from persisted owned adoption/catalog/frame/approval/run/profile/fee/plan identities, never fixture issuers, caller booleans or generic verifier callbacks. The verifier retains mutable run/BYOK/credential and approval/call row locks through commit, and reads their final authority in the same SQL snapshot as configuration ownership and DB time. ToolStore completion uses one BYOK-locked transaction for run and call updates. Configuration/invitation/profile/clock drift or a terminal/failed run rolls back admission. Status, sanitized account runtime metadata and local revocation/cleanup remain available without admission keys. Runtime metadata exports only owned identifiers and states, excluding manifest bodies, arguments, intent bindings and keys.

The minimal protocol adapter uses the public validator from exact `@ai-sdk/mcp@2.0.78`; it never constructs that package's client or transports. Supported protocol is2025-11-25, stateless JSON-only, synchronous bounded text/structured output. No tools/list, pings/replies, redirects, SSE, tasks, sessions, retry, reconnect, resume or remote teardown is permitted. Unsupported responses fail closed. Remote text and metadata stay untrusted data and never become model instructions.

Version2 requests/evidence bind operation/frame/request/body/manifest/full-profile identities. Broker policy pins upstream TLS/DNS and the protocol header; it accepts no caller URL or arbitrary header. Legacy version1 wire behavior is retained for legacy profiles; reviewed runtime profiles require version2 and reject downgrade before dispatch. Valid initialized notifications require an empty202/204 acknowledgement. Ed25519 evidence authenticates transport completion only, not actual cost or remote-resource termination. A valid synchronous terminal response changes the ledger to `completed_unreconciled`, freeing only the outbound transport slot. The full reserved exposure and period commitments remain, incurred minima are not reduced, and no billing receipt/refund/zero-cost settlement is fabricated. Only a future independently authentic billing verifier could reconcile those amounts. Completion cannot clear an existing global stop.

Any observed timeout, cancellation after entry, replay ambiguity, invalid proof or protocol violation retains a held financial liability and stops further funded activity. Entered frames are never automatically redispatched. A fresh completed invocation returns its bounded result only to that caller. Replaying a fully completed execution returns status with `result:null`; results are not persisted or redispatched. A crash after entry and before dispatch retains the full entered liability; configuration-independent `retainUnknown` explicitly marks an owned orphaned frame held and sets the global stop. Hosted orphan recovery remains an activation gate. Cancellation can release only durable never-entered reservations. Account/connection/adoption deletion may erase owned metadata but never financial rows, commitments or anonymous transport evidence. Native PostgreSQL contention, actual endpoint/fee/capacity evidence, real broker key provisioning, durable replay/mTLS and hosted recovery remain launch gates; no paid call or live activation is established by local checks.
