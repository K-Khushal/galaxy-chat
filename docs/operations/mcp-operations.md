# MCP operation accounting: offline preparation only

Production reservation, entry and receipt reconciliation return `mcp_operation_authority_unavailable`. There is no deployment flag, transport wiring, route, model tool, OAuth issuer, real catalog/action/approval issuer, trusted receipt issuer or verified fee schedule in this slice. No request body, token, credential, raw source or provider response is stored in the ledger. Synthetic fixture amounts demonstrate accounting behavior; they are not actual prices or all-in hosting cost proof.

`createMcpOperationStore` exposes owned sanitized status/export, reserved cancellation with a durable zero-entry state, and retention of unknown entered outcomes. `createFixtureMcpOperationStore` exists only for offline tests: construction and every authority-dependent admission, entry, period-bootstrap, issuance and reconciliation require `NODE_ENV=test`. Required future typed authority/receipt ports describe structured exact identities; production implementations are unavailable and caller-supplied verification callbacks are not accepted. The fixture issuer persists owner, connection, intent/catalog/action/approval and fee bindings. Every fixture `mcp.call` requires approval. Grants are immutable and consumed atomically once with committed entry. The same approval cannot be reissued after owner deletion because anonymous entered identities also retain its single-use evidence.

Every mutation runs READ COMMITTED and locks shared funding 41021406 before BYOK 41021407. The merged shared plan assertion is called in the same transaction with zero incoming credit charge: it validates existing credit allocation, frozen credit carry and global arithmetic including the whole Amcp allocation. The MCP ledger separately bounds deduplicated MCP exposure by Amcp. It does not reserve another platform budget or modify credit Lcarried, guest history, daily credit limits, existing financial holds or immutable reviewed plans.

Reservation binds immutable owner-derived versioned HMAC actor, exact connection revision, canonical full profile digest and purpose, catalog/schema and action revisions/digests, required approval, request digest and bounded bytes, deadline/one attempt, shared plan/capacity and complete fee snapshot. OAuth's five distinct purposes are denied because canonical connection ownership currently covers only the four MCP purposes; an MCP binding never grants OAuth authority. Fee configuration is strict, required and expiring: finite integer upper bounds, explicit all-in coverage/proof references, exact selected capacity digest, request/response, CPU/wall and one-attempt bounds. Missing costs never imply zero. Root-approved ceilings are owner/global active 1/2, UTC-day requests 10/50, retained records 100/1000; tighter selected values and actual profile/F13 byte/time limits win. These selected values are part of the fee capacity digest. Record/request counters persist after cancellation, settlement and owner deletion.

Final validations sample DB wall time together with control, owner/connection and persisted authority; after all awaited plan checks, writes and audit, the store synchronously rereads authoritative runtime configuration and checks complete identity, expiry, current invitation and limits. Per-call configuration overrides and transport callbacks are absent. Identical owned idempotent replay returns persisted state without entry. A committed entry has one attempt and cannot replay after a crash. Cancellation is allowed only for a durable reserved row with zero attempts. Post-entry expiry, abort, disconnect, errors and deletion never establish zero remote cost or permit releasing unknown liability.

Anonymous operations, immutable receipts, period commitments, audit and actor-key fingerprints have no cascading user/connection references. Only owner-access aliases/mappings and fixture authority metadata cascade. Account export contains only owned operation ID/state/revision/amount/attempt/time. Key rotation requires all previously registered key versions and matching fingerprints; an existing alias keeps its original actor key. Missing or changed historical keys deny new admission; global anonymous counters and liabilities never reset. There is no key-retirement or financial deletion procedure.

Period bootstrap is an explicit internal operator procedure with the exact reviewed shared-plan identity and complete sorted source commitments, never an endpoint or admission side effect. The fixture setup invokes it explicitly. A period source minimum is immutable, including sources admitted in that period: cancellation or late settlement cannot shrink it. For each source, carry takes the maximum of known obligation and every prior frozen amount, then sums each source once. Three historical carry rows for one source are not three independent bills. Repeated bootstrap is idempotent; changed or increased prior exposure denies an insufficient frozen period. No carry release or automatic supplementation is implemented without approved billing attribution authority.

Only persisted, exact operation/binding-bound fixture receipt evidence can settle an entered/held operation. Identical receipt repeats return the terminal state; conflicts fail. Full verified incurred amounts are retained, including valid integer overruns above the reservation. Recording an unknown entered outcome or a verified overrun atomically sets the global funding stop. Neither status nor conservative cleanup requires new admission to remain enabled. Settled/released evidence, anonymous record counts and frozen commitments are never deleted to recover capacity or money.

Offline evidence uses actual migrations and queued PGlite SQL through the captured application driver, with deterministic barriers after real queries. This proves rollback, persistence, identity, caps, retention and accounting behavior. It does not prove independent PostgreSQL backend contention, authentic live receipts, actual all-in cost, broker execution, queue delivery, host capacity or remote cancellation. Native PostgreSQL contention, reviewed pricing/capacity and each real authority implementation, billing-period attribution, funded hosting and recovery tests remain separate launch gates. No production execution can be enabled by this ledger alone.
